# 関西春ロボ2027 PC–マイコン間 CAN プロトコル v1（案）

PCはCANableでマイコンに指令を送ります。マイコンはCAN IDから対象を選び、接続先のESCやサーボに合わせて変換します。この仕様のIDとデータ形式は **PC–マイコン間** に適用します。RoboMasterのESCや近藤サーボとの通信には、それぞれの機器の方式を使います。

配線とUbuntuでの操作は [CANセットアップ](CANセットアップ.md) を参照してください。

## 各ビット欄に入れる値

**7つの欄を選び、左から順番に詰めるとCAN IDになります。** 数値は0x付きが16進数、それ以外は10進数です。ビット番号は右端から0で数えます。

| ビット位置 | 入れる欄 | 選ぶ値 |
|---|---|---|
| 28〜27（2ビット） | priority・優先度 | 0＝駆動無効化、1＝通常指令、2＝実測値、3＝通信確認 |
| 26〜24（3ビット） | kind・通信の種類 | 0＝指令、1＝実測値や状態、2＝診断要求、3＝診断応答 |
| 23〜20（4ビット） | board・基板番号 | PCとマイコンで決めた0〜15。指令では宛先、応答では送信元 |
| 19〜16（4ビット） | device・機器の種類 | 0＝基板自体、1＝M2006、2＝M3508、3＝近藤6000番台、4＝汎用ESC |
| 15〜12（4ビット） | instance・個体番号 | 同じ基板・同じ種類の中で決めた0〜15。例としてFL=0、FR=1、RL=2、RR=3 |
| 11〜4（8ビット） | op・操作 | 下表から選択 |
| 3〜0（4ビット） | version・仕様の版 | 必ず1 |

基板自体への指令や診断ではdeviceとinstanceは両方0です。実測値ではpriority=2とkind=1、診断要求ではpriority=3とkind=2、診断応答ではpriority=3とkind=3を組み合わせます。

| 操作 | op入力値 | 8ビット表記 | データ |
|---|---|---|---|
| 駆動無効化 | 0x01 | 00000001 | なし |
| 駆動許可 | 0x02 | 00000010 | なし |
| 速度指令 | 0x10 | 00010000 | float32、rad/s |
| 電流指令 | 0x11 | 00010001 | float32、A |
| 位置指令 | 0x12 | 00010010 | float32、rad |
| デューティ指令 | 0x13 | 00010011 | float32 |
| 実測速度 | 0x20 | 00100000 | float32、rad/s |
| 実測電流 | 0x21 | 00100001 | float32、A |
| 実測位置 | 0x22 | 00100010 | float32、rad |
| 基板の状態 | 0x23 | 00100011 | 1バイト。0＝無効、1＝許可、2＝異常 |
| 診断要求・応答 | 0xF0 | 11110000 | 同じ1バイトを送り返す |

float32のデータ長は4バイトです。操作に対応する機器の組み合わせは後述の指令表に従います。たとえばM3508には速度または電流指令、近藤サーボには位置指令を使います。

### 例　基板0・左前M3508に速度を送る

| 欄 | 入力値 | 2進数 |
|---|---|---|
| priority | 1（通常指令） | 01 |
| kind | 0（指令） | 000 |
| board | 0（基板0） | 0000 |
| device | 2（M3508） | 0010 |
| instance | 0（左前の割り当て例） | 0000 |
| op | 0x10（速度） | 00010000 |
| version | 1 | 0001 |

この順で29ビットを並べます。0x10は10進数では16です。

```text
priority kind board device instance op       version
01       000  0000  0010   0000     00010000 0001

16進数のCAN ID = 08020101
```

+1.0 rad/sならデータはリトルエンディアンのfloat32で「00 00 80 3F」です。速度だけを変える場合、IDは同じです。フレームの表記例は次のようになります。

```text
08020101#0000803F
^^^^^^^^ ^^^^^^^^
CAN ID   データ4バイト
```

cansendではIDを8桁で指定すると拡張フレームになります。29ビットを8桁の16進数で表すと余る最上位3ビットは0です。実バスで最初に試すのは第5節の診断要求にしてください。

| 取付場所 | board | device | instance | op |
|---|---|---|---|---|
| 左前 | 未確定 | 未確定 | 未確定 | 未確定 |
| 右前 | 未確定 | 未確定 | 未確定 | 未確定 |

## 1. 通信の基本

| 項目 | 仕様 |
|---|---|
| バス | Classic CAN、**1 Mbit/s** |
| ID | **29ビット拡張ID**。データフレームを使用 |
| データ | 0〜8バイト。複数バイトの数値はリトルエンディアン |
| float32 | IEEE 754単精度。NaNと無限大は無効 |

## 2. CAN IDの読み方

上位ビットから **優先度 → フレーム種別 → 基板 → デバイス種別 → 個体番号 → 操作 → 版** の順に並びます。

| ビット | 幅 | フィールド | 意味 |
|---|---:|---|---|
| 28–27 | 2 | priority | 0＝駆動無効化、1＝指令、2＝フィードバック、3＝診断 |
| 26–24 | 3 | kind | 0＝指令、1＝フィードバック、2＝診断要求、3＝診断応答。4〜7は予約 |
| 23–20 | 4 | board | 基板番号。0〜15。指令と診断要求では宛先、返信とフィードバックでは送信元 |
| 19–16 | 4 | device | デバイス種別。下表を参照 |
| 15–12 | 4 | instance | 同一基板・同一種別内の個体番号。0〜15 |
| 11–4 | 8 | op | 操作コード。後述 |
| 3–0 | 4 | version | この仕様では1 |

同じ拡張データフレーム同士では小さいIDが優先されます。値がフィールドの範囲外なら送信前にエラーとします。

```python
can_id = (
    (priority << 27) | (kind << 24) | (board << 20)
    | (device << 16) | (instance << 12) | (op << 4) | 1
)
```

| device | 機器 | 初期実装で使う操作 |
|---:|---|---|
| 0 | 基板自体。instanceは0 | 駆動無効化・駆動許可・通信確認 |
| 1 | RoboMaster M2006 | 速度、電流 |
| 2 | RoboMaster M3508 | 速度、電流 |
| 3 | 近藤サーボ6000番台 | 位置 |
| 4 | 汎用ブラシレスモーター＋ESC | デューティ指令。対応ESCなら速度 |
| 5〜15 | 予約 | チームで割り当て |

個体番号は機器固有IDとは別です。マイコン側で「種別・個体番号 → 接続ポートやESC ID」を対応づけます。近藤サーボは型番に合わせて位置の原点・範囲・変換を設定します。汎用ESCの入力方式、逆転の可否、ニュートラル、アーミング条件も実機ごとに設定します。

## 3. 指令とフィードバック

指令は `kind=0` です。駆動無効化だけ `priority=0`、残りは `priority=1` を使います。

| op | 対象 | 内容 | ペイロード |
|---|---|---|---|
| `0x01` | 基板 | 基板配下の駆動を無効化 | DLC 0 |
| `0x02` | 基板 | 基板配下の駆動許可を要求 | DLC 0 |
| `0x10` | M2006 / M3508 / 対応ESC | 目標速度 [rad/s] | DLC 4、float32 |
| `0x11` | M2006 / M3508 | 目標電流 [A] | DLC 4、float32 |
| `0x12` | 近藤サーボ | 目標位置 [rad] | DLC 4、float32 |
| `0x13` | 対応ESC | 正規化したデューティ指令 | DLC 4、float32。0＝ニュートラル。逆転対応は −1〜+1、片方向は0〜+1 |

足回りの**速度は車輪軸基準、前進方向を正**とします。モーターの取付方向と減速比はマイコン側で変換します。電流の符号も前進方向にトルクを出す向きを正とします。位置はサーボごとに機械原点と正方向を登録します。カタログ値やESC設定に合わせた速度・電流・位置上限は、機器ごとに決めます。

フィードバックは `kind=1, priority=2` を使います。取得できる項目だけ送信します。

| op | データ | ペイロード |
|---|---|---|
| `0x20` | 実測速度 [rad/s] | DLC 4、float32 |
| `0x21` | 実測電流 [A] | DLC 4、float32 |
| `0x22` | 実測位置 [rad] | DLC 4、float32 |
| `0x23` | 基板の駆動状態 | DLC 1、uint8。0＝無効、1＝許可、2＝異常 |

## 4. 足回りの割り当て例

基板0にM3508が4台つながっている場合の例です。M2006を使う輪は `device=1` に差し替えてIDを計算します。

| 車輪 | instance | 速度指令ID | 速度フィードバックID |
|---|---:|---|---|
| 左前 FL | 0 | `08020101` | `11020201` |
| 右前 FR | 1 | `08021101` | `11021201` |
| 左後 RL | 2 | `08022101` | `11022201` |
| 右後 RR | 3 | `08023101` | `11023201` |

速度0のデータは `00 00 00 00`、+1.0 rad/sは `00 00 80 3F`、−1.0 rad/sは `00 00 80 BF` です。Pythonでは `struct.pack("<f", speed)` で生成できます。

ROS 2の `data_processor` は現在、スティック入力を基準にした値を出力します。車輪の上限と入力範囲を決めてrad/sに変換してから速度指令に載せます。PIDがPC側にある構成では、CANの速度フィードバックをPIDへ渡し、その出力を電流指令として送る方式を使えます。各車輪に対して有効な制御モードは1つに固定します。

## 5. 駆動を使わずに通信を確認する

診断の `op=0xF0` は基板の応答確認です。要求は `kind=2`、応答は `kind=3`。どちらも `priority=3, device=0, instance=0, DLC=1` とし、マイコンは受け取った1バイトをそのまま返します。駆動状態は変化しません。

| 方向 | 基板0のID | ペイロード例 |
|---|---|---|
| PC → マイコン | `1A000F01` | `A5` |
| マイコン → PC | `1B000F01` | `A5` |

```bash
cansend can0 1A000F01#A5
```

別端末の `candump can0` で **応答ID `1B000F01` と `A5`** が揃うことを確認します。この確認にはマイコン側への診断応答の実装が必要です。

## 6. 駆動をつなぐ前に決めること

- マイコンは起動時に駆動を無効とし、異常が解除されていて指令が中立のときにだけ、明示的な駆動許可要求を受け付けます。無効化後は古い指令を破棄します。
- 最後に受理した有効な指令からの経過時間をマイコン側で監視します。無効フレームや診断フレームでは監視時間を更新しません。途絶やCAN異常では駆動を無効化し、新しい許可要求を待ちます。
- 送信周期とタイムアウトは、通信遅延と実機が指令を失った際の停止要件から決めます。駆動なしの試験で、PC側の送信停止、マイコン再起動、異常解除後の再開条件を検証します。
- 未対応の版・操作・DLC・値の範囲は指令として受理しません。機器ごとの無効化動作と物理的な非常停止の経路もチームで確認します。
